BẠN ĐANG XÂY GÌ?

Một agent biết kiểm tra trước khi kết luận.

Người dùng hỏi GitHub hoặc Cloudflare có sự cố gì, ảnh hưởng dịch vụ nào và có liên quan đến lỗi của họ không. Bạn tự viết vòng lặp Python để model chọn tool, đọc bằng chứng, tìm tiếp khi cần rồi trả lời có nguồn và nêu phần chưa biết.

Agent kiểm tra trạng thái dịch vụ công khai, không đăng nhập tài khoản GitHub hay xem workflow trong repo cá nhân. GitHub Actions ở đây là tên dịch vụ của GitHub.

① Câu hỏi→② Model chọn tool→③ Python chạy tool→④ Kết quả về model↺⑤ Trả lời + nguồn

Hai tool mà model được gọi

Tool / tham sốDùng để làm gì?Giới hạn cần nhớ
get_status(provider, component)Ví dụ: github, ActionsXem trạng thái tổng thể, component khớp, danh sách incident và ID.Tìm chuỗi trong 50 incident gần nhất, trả tối đa 5 incident khớp. Dùng tên component ngắn; rỗng chưa chứng minh không có sự cố.
get_incident_details(provider, incident_id)Đọc trạng thái, phạm vi, các cập nhật, thời gian và URL nguồn của một incident.Chỉ tra được incident trong cửa sổ dữ liệu. Trả hai update mới nhất và update đầu tiên; mỗi update tối đa 900 ký tự. Xem truncated và updates_total.

tools.execute(name, args) là hàm Python định tuyến lời gọi đến tool tương ứng. Nó không phải tool thứ ba mà model được giới thiệu.

Bốn thứ dễ nhầm

  • Snapshot / live: snapshot là dữ liệu đã lưu để so sánh các lần eval công bằng hơn; live gọi status API thật. UI này đọc lại trace snapshot đã lưu.
  • Status / incident: dịch vụ đang operational trong snapshot vẫn có sự cố lịch sử resolved. Đọc một incident cũ không đủ xác nhận trạng thái dịch vụ.
  • Model / tool: model yêu cầu gọi hàm; Python thực thi hàm. Một lượt model có thể yêu cầu nhiều tools, rồi nhận tất cả kết quả về đúng tool_call_id.
  • Trace / suy nghĩ: trace là nhật ký lời gọi và kết quả quan sát được, không phải suy nghĩ nội bộ của model. Các trường step bắt đầu từ 0.

Đọc một case trên giao diện

  1. Đọc câu hỏi và phân biệt yêu cầu hỏi trạng thái, incident hay cả hai.
  2. Xem từng lượt: model trả tool_calls, Python chạy hàm với arguments nào, tool trả gì.
  3. Model trả stop và không còn call thì mới xét hoàn thành; có thể phải sửa nguồn trước. Hết max_steps thì chưa hoàn thành.
  4. Đối chiếu final answer, nguồn, dữ liệu thiếu hoặc bị cắt và nhận xét judge.

37 unit tests kiểm tra code offline. 22 case eval gọi model thật để kiểm tra hành vi. Điểm gồm chính xác 40, đầy đủ 25, bằng chứng 20, giới hạn suy luận 15; kiểm tra bằng code có thể áp trần điểm. completed không bảo đảm trả lời đúng.
